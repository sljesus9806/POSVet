El cliente destino corre en **una sola PC con Windows**: esa PC es el servidor y la persona entra por **Chrome a `http://localhost:3000`** (favorito). El **empaquetado de escritorio Electron falló al construir el `.exe`** (electron-builder/NSIS), así que se descartó. Pivoteo: scripts de Windows en `deploy/windows/` (PR #36 **MERGEADO 2026-06-08**, rama `chore/deploy-windows-local`): `instalar.ps1` (una vez: Node+PostgreSQL por winget como servicio, crea BD, genera `.env` prod, `npm ci`+build+`migrate deploy`+seed, instala licencia, registra autoarranque) e `iniciar.ps1` (cada login: levanta `next start` en puerto fijo y abre el navegador). Postgres = **servicio de Windows** (no embebido, no Docker).

**Why:** Es lo más simple y estable para una sola compu sin conocimientos técnicos; el uso diario queda 100% sin internet.

**How to apply:** Dos cosas SIEMPRE muerden — (1) **Candado de licencia**: en producción (`next start`), sin licencia instalada el layout redirige a `/licencia` y bloquea (el bypass de dev NO aplica en producción). Hay que emitir token offline en la PC con la llave privada (`npm run lic:emitir -- --cliente "X" --modo offline --meses 120`) y dejarlo en `deploy/windows/licencia.token` antes de instalar. (2) **El build se hace en Windows**: el motor binario de Prisma es por SO, no se puede mandar precompilado desde Linux → por eso el instalador construye en la PC del cliente. Solo la instalación necesita internet (bajar Node/PG/deps).

**2026-06-08 (en Windows real):** validado el tramo de build del instalador en esta PC — `npm ci` ✓, `npx prisma generate` (motor Windows, Prisma 6.19.3) ✓, `npm run build` ✓ (exit 0). El build resultó **independiente de la BD**: TODAS las rutas compilan como `ƒ` dinámicas (solo `/licencia` estaba forzada, las demás se vuelven dinámicas por `auth()`), así que compiló incluso con un `DATABASE_URL` a una BD inexistente. Además **endurecí `instalar.ps1`**: reordené a migrate-deploy + seed ANTES del build (belt-and-suspenders por si en el futuro hay una página pública estática que toque BD), resolví `npm`/`npx` a sus `.cmd` explícitos, y mejoré el aviso de "sin licencia". **GOTCHA de encoding (2026-06-09, primer run real en la PC del cliente):** `instalar.ps1` tronó con `Unexpected token` al PARSEAR (antes de ejecutar). Causa: los `.ps1` estaban en UTF-8 **sin BOM** y tienen em-dashes `—`/acentos/`…`/`✓`; **PowerShell 5.1 lee sin-BOM como ANSI/CP1252** → el byte `94` del em-dash se vuelve comilla tipográfica `"` que PS toma como cierre de cadena y desincroniza el parser. Fix: reguardar `instalar.ps1` e `iniciar.ps1` como **UTF-8 CON BOM** (commit en PR #39). REGLA: todo `.ps1` de este repo debe ir con BOM (o ASCII puro). Verifica con `[System.Management.Automation.Language.Parser]::ParseFile($f,[ref]$null,[ref]$errs)`.

**2026-06-09 — instalador probado de verdad en la PC Windows del usuario (PostgreSQL 18 ya instalado):** funciona hasta el final salvo la licencia. Hallazgos/fixes (todos en PR #39): (1) parse error → BOM (ver arriba). (2) Password de `postgres`: el usuario dio una equivocada; psql daba "password authentication failed" — re-correr con la correcta. (3) `migrate deploy` dio **P1001 transitorio** (la BD SÍ está en 5432, escucha 0.0.0.0 + ::; psql conecta) → endurecido con wait-de-conexión + reintento ×3 y `DATABASE_URL` con `127.0.0.1` (no `localhost`, que en Windows resuelve a ::1 y a Prisma a veces le da P1001). Validé a mano: `prisma migrate deploy` aplicó las 14 migraciones ✓, `prisma db seed` ✓ (admin@posvet.local, 70 permisos ADMIN, productos demo), y `next start` arranca y sirve (`/login` 200, `/` 307→/login, `/licencia` 200, `/dashboard` 307; CSS `/_next/static/*.css` 200). (4) **Aviso benigno:** `next.config` tiene `output:"standalone"` (por Electron/SaaS) y `iniciar.ps1` usa `next start` → Next avisa "next start does not work with standalone", PERO sirve bien (build completo en `.next`); NO cambiar a `node .next/standalone/server.js` (eso exige copiar static/public a mano).

**BLOQUEANTE real para uso/cliente: la LICENCIA.** El instalador termina pero la app queda en `/licencia` sin token, y aquí NO se puede emitir uno válido porque la llave privada local no empareja con `keys.ts` (ver [[licenciamiento-anticrack]], gotcha 2026-06-09). Antes de instalar en la compu del cliente: recuperar la llave privada REAL de un respaldo, `npm run lic:emitir -- --cliente "X" --modo offline --meses 120`, y dejar el token en `deploy/windows/licencia.token`.

**Respaldos automáticos (2026-06-09, PR #39):** `deploy/windows/respaldar.ps1` (pg_dump `-Fc` comprimido, lee creds del `.env`, purga >N días) + `restaurar.ps1` (pg_restore `--clean --if-exists`, destructivo). `instalar.ps1` los registra como **Tarea Programada SYSTEM** `Ligerito - Respaldo BD` cada 30 min (params `-RespaldoDestino` default `C:\Ligerito-Respaldos`, `-RespaldoDias` default 7). Validado: respaldar.ps1 genera dump real ✓, sintaxis del trigger 30-min ✓ (registro user-level); SOLO sin probar el registro con principal SYSTEM (necesita admin, no se corrió en la PC dev). Instructivo en `deploy/windows/INSTRUCTIVO-CLIENTE.html`/`.pdf`.
